# Building Vanillish for Windows

## The short version

1. **Actions → vanillish-windows → Run workflow.** One Windows runner builds everything. Estimates:
   about 50–80 minutes the first time, about 15–25 once the cache is warm.
2. Download the run's artifact `Vanillish-<commit>-windows-x64.zip`. It is the zip itself, under
   its own name.
3. Extract it to a folder of your own (`C:\Games\Vanillish`, never Program Files) and open
   `Vanillish.exe` ([WINDOWS.md](WINDOWS.md#install)).

The workflow has no tag trigger, so a `vanillish-v*` release is still the APK alone. It can be
called (`workflow_call` with `release-tag`): that is how a release will attach the zip beside the
APK without a second workflow racing to create the same GitHub Release. The zip is not code-signed.

## How the build goes

| step | what | why |
|---|---|---|
| `cargo test -p inilla-core -p inilla-platform` | the engine-free tests, on Windows | the DPAPI round trip, the Windows paths and every pure helper run here; Linux can only compile their Windows arms |
| `cargo clippy … --target x86_64-pc-windows-msvc --no-deps` | lints the entry and inilla-platform, and runs the entry's build script | a broken `windows/vanillish.rc` fails in minutes, before the long build |
| `windows/build-exe.sh` | `cargo build --profile windows --target x86_64-pc-windows-msvc -p vanillish-windows`, with `+crt-static` | one exe; a PC needs no Visual C++ Redistributable |
| — its checks (`llvm-readobj`) | the exe must be AMD64 and use the GUI subsystem (the console one for `dev`), with an 8 MB main-thread stack. Its imports must be Windows' own DLLs only and none of the C runtime's. It must carry icon group 1, a version and a manifest. A `vanillish.pdb` must exist. | an unexpected import fails by name, so the allow-list widens on purpose. Windows' default stack is 1 MB, against 8 MB on macOS and Linux, and Update runs on the main thread. |
| — the package | it stages `Vanillish/`: `Vanillish.exe`, `vanillish.pdb`, `README.txt`, the licences and the 512 px art. It then writes the zip, `symbols/`, `build-notes.md` and `build.env`. | the PDB beside the exe lets a crash report's backtrace name functions |

**The `windows` profile** (root `Cargo.toml`): release optimisation, no LTO, as for Android and iOS.
It sets `strip = false`, because a stripped MSVC link writes no PDB. Rust points the exe at its PDB
by file name alone, so the copy beside it is found.

**The resources.** `crates/vanillish-windows/build.rs` compiles `windows/vanillish.rc` with
`embed-resource` on an MSVC target. It embeds:

- the icon `windows/Vanillish.ico`, generated by `windows/tools/make-icon.py` from the Android
  launcher's vectors and committed;
- the manifest `windows/vanillish.manifest`: asInvoker, PerMonitorV2, long paths, the UTF-8 code
  page;
- the version: `VANILLISH_VERSION_NAME`, else the workspace version and the commit, with
  `VANILLISH_CI_BUILD` as the fourth number.

The gnu target, the Linux cross check, embeds none of this.

## Building locally

On a Windows PC, in Git Bash:

- rustup (the toolchain is `rust-toolchain.toml`'s);
- Visual Studio's C++ build tools, with a Windows SDK (for `rc.exe`);
- LLVM (`llvm-readobj`; `winget install LLVM.LLVM`);
- Python 3.

```sh
windows/build-exe.sh                         # → target/vanillish-win-out/Vanillish-<commit>-windows-x64.zip
VANILLISH_FEATURES=dev windows/build-exe.sh  # benilla's dev instruments and a console
```

For a quicker loop, `cargo run -p vanillish-windows --features dev` builds the dev exe in the dev
profile and runs it with its console. benilla's own `cargo run -p benilla` stays benilla's desktop
build; on a Windows host a `--workspace` build (upstream's gates) turns the `vanillish` feature on
for every member through this crate, so run those with `--workspace --exclude vanillish-windows`.

| knob | what |
|---|---|
| `VANILLISH_VERSION_NAME` | a release's version (`0.3.0`): the zip's label, the exe's version resource and the version the app shows; else the commit |
| `VANILLISH_CI_BUILD` | the version resource's fourth number (the CI run number) |
| `VANILLISH_FEATURES` | `dev`, or empty for the player build |
| `VANILLISH_PROFILE` | another Cargo profile than `windows` |
| `VANILLISH_EXE` | check and package this `vanillish.exe` (and the `.pdb` beside it) instead of building one |

## Checking from Linux

The Windows code is `cfg(windows)`, which the Linux gates never compile. `vanillish-check` and the
AGENTS.md list cross-check it for `x86_64-pc-windows-gnu`:

```sh
source windows/toolchain/linux-env.sh
cargo check --target x86_64-pc-windows-gnu -p vanillish-windows
cargo clippy --target x86_64-pc-windows-gnu -p inilla-platform -p vanillish-windows --no-deps -- -D warnings
cargo clippy --target x86_64-pc-windows-gnu -p benilla-app --features vanillish --all-targets -- -D warnings
```

`linux-env.sh` uses the same pinned Zig wheel as the iOS sysroot (`ios/toolchain/linux-env.sh`).
It takes the wheel's mingw-w64 headers for the graph's C (Lua, ring), with no Microsoft SDK, and
unpacks into `target/vanillish-win-toolchain/` (`VANILLISH_WIN_TOOLCHAIN` moves it). A check needs
no link. The shipping exe is MSVC, built on Windows.

## CI

| workflow | when | what |
|---|---|---|
| `vanillish-check.yml` | every push and PR | among the rest, the Windows cross check and clippy for x86_64-pc-windows-gnu |
| `vanillish-windows.yml` | Run workflow; called by a release later | the Windows tests, clippy for MSVC, `Vanillish.exe` and the zip |

Artifacts are kept 14 days:

- `Vanillish-<label>-windows-x64.zip`;
- `Vanillish-windows-symbols-<commit>` (the PDB and its commit).

A Windows runner costs 2× Actions minutes on a private repository (`ios/tools/actions-budget.sh`
counts it); on a public one, standard runners are free.

## Signing

None yet. An unsigned exe meets SmartScreen ("More info → Run anyway"), and its reputation resets
with every release. Windows 11's Smart App Control blocks it outright.

The options, for a later round, are:

- the SignPath Foundation (free for open-source projects that qualify);
- Azure Artifact Signing (paid; individuals in the US and Canada, organisations in more countries);
- an OV certificate.

Signing would be a packaging step behind optional secrets, never in the step that runs build
scripts.
